# Technical Report: Document Search and Summarization Using LLMs

## 1. Objective and scope
This project implements retrieval-augmented summarization over a news-article corpus. Given a natural-language query, it ranks relevant documents using lexical and semantic retrieval, then generates a configurable-length synthesis with an instruction-tuned language model. The implementation is in `Text_Summarizer.ipynb`; a Streamlit app is generated by a notebook cell. Results below are transcribed from the committed notebook's saved outputs, not independently rerun.

## 2. Dataset and preprocessing
**Source:** CNN/DailyMail 3.0.0, Hugging Face `abisee/cnn_dailymail`, training split. The notebook shuffles with seed 42 and selects 25,000 candidate articles, retaining up to 20,000 after cleaning.

Cleaning removes selected CNN/author/date prefixes, URLs and HTML-like tags, normalizes quotation marks, and collapses whitespace. Articles outside 100–1,500 words are filtered out. Deduplication hashes the lowercased first 200 characters; this catches identical openings but is **not** comprehensive near-duplicate detection. Searchable article text is stored separately from reference `highlights`, preventing direct summary leakage into retrieval text. The notebook reports 20,000 indexed articles and 2 residual boilerplate prefixes in its inspection.

**Rationale:** text normalization reduces formatting noise, filtering avoids unusually short/long examples, and deduplication reduces redundant search results. Truncation later limits inference cost, but may omit relevant material.

## 3. Architecture and methodology
Pipeline: **query → BM25 and/or dense retrieval → reciprocal rank fusion → top-N articles → Qwen summary**.

### 3.1 Indexing
- **Lexical:** regex word tokenization (lowercase `\\w+`) and `rank_bm25.BM25Okapi`.
- **Dense:** `BAAI/bge-small-en-v1.5` sentence embeddings, encoded in batches of 128 and L2-normalized; `faiss.IndexFlatIP` performs exact inner-product search (equivalent to cosine similarity for normalized vectors).
- **Persistence:** `docs.pkl`, `bm25.pkl`, and `cnn_dm.faiss` are written locally for reuse. These large generated artifacts are not committed.
- **Fusion:** top-50 candidates from each retriever are combined by reciprocal rank fusion with constant 60. The search function supports `bm25`, `dense`, and `hybrid` and returns top N ranked article texts with scores.

Exact FAISS retrieval is simple and accurate for this scale, but memory and search work increase with corpus size.

### 3.2 Summarization
The final notebook configuration loads `Qwen/Qwen2.5-3B-Instruct` through Hugging Face Transformers, generates deterministically (`do_sample=False`), and prompts for a factual combined summary restricted to retrieved text. Presets are approximately 50, 120 and 250 words, or an integer target. Each article is truncated to its first 400 words before prompting to control context and latency.

**Implementation caveat:** an earlier notebook cell uses Gemini and Colab Secrets before the later Qwen setup replaces its chain. Thus the committed notebook is not yet a clean, API-key-free top-to-bottom run; the Gemini section should be removed or made explicitly optional. The README's Qwen-only setup currently overstates reproducibility.

## 4. Evaluation design
A seeded random sample of 200 document IDs is designated for retrieval testing; those documents **remain in the indexed corpus** so queries can retrieve their source. Fifty of these IDs receive LLM-generated queries based on the first 300 article words. For each query, the rank of its source document is checked.

Metrics:
- **Recall@1 / Recall@5:** proportion of queries whose source document appears in the first 1 / 5 results.
- **MRR:** mean reciprocal rank of the source document (0 if absent from top 10).

For summarization, the notebook evaluates 30 individual documents with `rouge_score` against CNN/DailyMail human-written highlights, comparing Qwen-generated approximately 50-word summaries against a **Lead-3** baseline (first three sentences). Ten generated summaries receive one human rater's 1–5 scores for relevance, coherence and faithfulness.

These are small, single-run samples; the generated queries often contain source-specific terms. Consequently, the retrieval scores should not be interpreted as general search relevance across arbitrary user queries.

## 5. Results
### 5.1 Retrieval (50 source-document queries)
| Method | Recall@1 | Recall@5 | MRR |
|---|---:|---:|---:|
| BM25 | 0.98 | 1.00 | 0.987 |
| Dense | 0.94 | 1.00 | 0.970 |
| Hybrid RRF | 0.96 | 1.00 | 0.977 |

BM25 leads on this query set. Hybrid retrieval does **not** improve on BM25 here, though it may be useful for paraphrases or vocabulary mismatch. A future evaluation should include independently written and paraphrased queries, with graded relevance judgments and nDCG.

### 5.2 Summary quality (30 documents)
| Method | ROUGE-1 F1 | ROUGE-2 F1 | ROUGE-L F1 |
|---|---:|---:|---:|
| Lead-3 | 0.387 | 0.151 | 0.241 |
| Qwen2.5-3B-Instruct | 0.363 | 0.118 | 0.237 |

Lead-3 scores higher on all three lexical-overlap measures. This does not establish that Lead-3 is universally more coherent or useful; ROUGE does not fully measure factual accuracy or multi-document synthesis. The result is a limitation, not evidence of LLM superiority.

### 5.3 Human evaluation (10 summaries; one rater)
| Criterion | Mean / 5 |
|---|---:|
| Relevance | 3.8 |
| Coherence | 3.8 |
| Faithfulness | 3.7 |

Faithfulness is the weakest of the three dimensions. The individual scored CSV is not present in the repository, so the published means are currently supported by saved notebook output rather than independently inspectable rating records.

### 5.4 Efficiency observations
The notebook reports approximately **245.7 seconds** to encode the 20,000 articles and demonstrates a **5.4-second** short summary in one example. These are environment-specific observations, not benchmark guarantees. Index persistence avoids repeating embedding work on each query. The Streamlit implementation caches loaded resources, searches and summaries.

## 6. User interface (bonus)
A notebook cell writes a Streamlit application with query entry, hybrid/BM25/dense selection, 30–250-word slider, configurable top-N summarization, suggestions from article highlights, five-results-per-page navigation and expandable full text. The notebook records a local HTTP 200 response during a Streamlit launch, but this alone does not validate all UI interactions.

**Packaging limitation:** `app.py` is not committed as a standalone file; running `streamlit run app.py` directly after cloning will fail until the notebook writes it. Tunnel URLs shown in notebook output are temporary, not permanent hosting.

## 7. Challenges, mitigations and limitations
| Challenge | Implemented mitigation | Remaining limitation |
|---|---|---|
| Keyword/semantic mismatch | BM25 + BGE dense retrieval with RRF | Hybrid underperforms BM25 on current test |
| Large indexing workload | Batched embeddings, persisted indexes | Exact FAISS and in-memory BM25 scale poorly to millions |
| LLM resource use | Local 3B model, 400-word truncation, caching | GPU memory and latency remain significant |
| Summary hallucinations | Source-only factual prompt, greedy decoding | Faithfulness mean 3.7/5; no automated claim verification |
| Evaluation cost | 50 retrieval queries, 30 ROUGE cases, 10 human ratings | Small samples, one human rater, no confidence intervals |
| Reproduction | Seed 42, requirements, notebook | Gemini setup conflicts with Qwen-only README; versions unpinned |

## 8. Scalability and next steps
For larger corpora, switch FAISS from exact `IndexFlatIP` to an approximate IVF/HNSW index, and use an inverted-index engine such as OpenSearch for lexical search. Consider incremental ingestion, metadata filtering, chunk-level indexing with parent-document aggregation, a cross-encoder reranker, batch query processing and caching. Measure latency percentiles and memory consumption on a defined machine.

**Prioritized improvements:** (1) commit standalone `app.py`; (2) remove the mandatory Gemini cell or make it optional and align dependency installation; (3) commit small evaluation CSV files including raw human ratings; (4) evaluate human-written paraphrases and graded relevance; (5) add factuality checks and broader human scoring; (6) pin tested versions and validate a clean installation.
